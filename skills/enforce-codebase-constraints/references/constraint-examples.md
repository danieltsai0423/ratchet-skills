# 約束設計範例

## 依賴邊界

以桌面應用程式的 main 和 renderer 為例。先釐清哪一端擁有哪些能力，哪些型別可共享，以及呼叫需要經過哪個橋接介面。從正常打包設定或既有匯入解析器取得依賴圖。若規則要攔截跨界依賴，正反案例可包含直接 import、實際存在的路徑別名或重新匯出，以及合法的契約型別匯入。

讓目錄結構本身成為 context。例如頂層目錄直接以執行環境命名（`electron-renderer/`、`electron-main/`），兩者之間連型別都不互相匯入，共用型別放在獨立的 `shared/`；產品功能採一個功能一個資料夾；有特殊限制的路徑（例如每個 tick 都執行、不得配置記憶體的模擬迴圈）放在專屬目錄並對該目錄套用規則。

範例診斷：「renderer 依賴 main 的檔案存取實作。請改用 renderer 可呼叫的橋接介面。」

## API 誤用

先辨識原本使用的是衍生資料、事件觸發、外部狀態同步，或有業務意義的延時。以 React 與計時器為例，衍生資料可在渲染時計算，使用者動作可由事件處理器處理，外部系統同步可視需要使用既有 hook 或封裝。合法的排程與同步情境保留明確入口。替代介面可用後，讓限制精確匹配問題用法與區域。

## 註解與抑制

註解無法被強制執行，也容易過時，卻常被 Agent 用來為權宜修補辯護，例如「先延後釋放，以防它回來」配上 `setTimeout`，再被複製到共用模組而擴散。遇到用註解合理化的權宜修補，先找出被掩蓋的行為，例如事件順序、缺漏的等待條件或狀態所有權。讓診斷指向既有的事件／狀態介面或應補的契約。若問題是無限制的檢查抑制，檢查可辨識的抑制語法及其範圍，要求必要例外有具體理由。

專案若決定收緊註解政策，可用 lint 只允許有明確類別的註解，例如授權、公開契約、維護取捨和無法由型別表達的不變量，其餘意圖改由命名、型別或檢查表達。以註解總數或新增數作為收斂指標，先攔截新增再分批清除。
