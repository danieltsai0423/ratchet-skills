# 盤點 Agent 工程環境

1. 選出要改善的模組、關鍵流程或反覆出現的問題。查現行目錄與公開 API、實際啟用的檢查設定和 CI、測試入口及 Agent 規則。以檔案與行號、可重跑的命令或具體實例記錄證據。無法查證的項目標為待確認。
2. 用下表逐層追蹤同一個問題。層級由上到下成本遞增，從架構開始，找最早能可靠攔截問題的層，並指出它目前在哪個入口會生效。只有設定而未接上實際使用的命令或 CI 時，記錄為覆蓋缺口。
3. 優先處理影響大、已重複發生且有明確驗收條件的缺口。估計修改範圍、舊有用法和誤報成本。先挑出一個能驗證成效的切入點，例如先保護單一模組邊界，再按結果擴大。
4. 交付按優先度排列的清單，每項寫明問題、證據、介入層、建議產出、驗收方式與依賴。若考慮外迴圈，確認內迴圈已有可重現的失敗、有穩定的必要檢查、有能審查的證據，再評估擴大執行範圍。盤點以報告為交付，實作依任務授權。

| 層級 | 盤點問題 |
| --- | --- |
| 程式碼庫與架構 | 目錄、公開 API 和型別是否讓正確用法容易找到？是否有經常被複製的權宜寫法？ |
| 靜態分析與編譯 | 禁止的依賴或用法是否有明確訊號？哪個檢查會攔截？失敗訊息能否指引修正？ |
| 執行期與形式驗證 | 能否從正常入口重跑關鍵路徑？異常狀態或不變量有何證據？ |
| 自然語言規則 | 哪些要求需要領域判斷？哪些可移到已能執行、能驗證的機制？ |
| 人工審查 | 審查者目前還靠讀碼抓哪些問題？哪些可移到上面各層？審查是否先看驗證產物？是否定期抽樣閱讀近期合併的程式碼，找出正在被複製的新權宜寫法？ |

若缺少歷史資料，可先記錄違規數、誤報數或可重現失敗比例作為基準。用同樣的範圍與量測方式驗收改善。產量提升時，另以回退率、跨版本的效能基準與發版間隔確認品質沒有退化，並記錄已轉成自動檢查的糾正數。
