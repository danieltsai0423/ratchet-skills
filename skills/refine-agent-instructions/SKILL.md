# 精簡 Agent 規則

1. 找到實際生效的規則檔、作用目錄與優先序。逐條辨識它要防止哪種失敗、在哪裡適用、現有哪個命令或設定可能涵蓋它。以具體例外檢查同名規則是否真的等效，例如 linter 可能只檢查前端，文字規則涵蓋整個專案。
2. 對可機械判定的規則，查設定及實際執行入口，再用一個違規例與一個合法例比對適用範圍。已可靠覆蓋的規則可縮成通往檢查入口或權威設定的指引。尚有缺口的規則保留有效指示，列出要補的檢查和移除條件。
3. 對業務判斷、架構取捨、允許的例外、權限限制與非顯而易見的驗證入口，保留適用情境與行動。詳細流程放回既有權威文件或相應技能，用相對連結及觸發條件引導。若規則檔由單一來源產生，修改正本並沿用專案同步方式。
4. 依授權交付分析或修改。用有代表性的規則情境逐項檢查修改後仍能找到權威來源、執行必要檢查、辨識例外。回報已移到工具的規則、仍需文字指示的判斷及未覆蓋項目。

例如「所有 package 禁止循環依賴」需要比對 CI 是否掃到所有 package、測試及產生的程式碼。CI 只涵蓋部分範圍時，保留適用於其餘範圍的指示並指出缺口。

## 審核新增的文字規則

Agent 新增或建議新增規則、文件、技能或說明檔時，同樣走上面的流程，另外確認三件事：

- **來源**：每條規則能追溯到使用者要求、實際失敗或審查紀錄。為權宜做法辯護的說明，改為在程式碼中修正根因，並以檢查防止再犯。
- **範圍**：一次糾正只寫成它實際適用的情境與例外，保持與原始事件同樣的範圍，避免升格成全域硬規則。
- **歸屬**：可機械判定的要求先嘗試做成檢查；需要文字時寫進既有權威文件，並將任務未要求的新 Markdown 檔撤回或合併。
