# 以證據驗證軟體行為

1. 把每項驗收條件寫成可觀察主張，包含前置狀態、正常入口、操作及預期結果。從規格、功能地圖或實際介面確認操作詞彙。若需求含例外情境，記錄失敗、重試或狀態轉移後應維持的性質。
2. 用專案現有工具驗證，從能觀察該主張的最小層級開始。使用者流程走正常入口並觀察結果。輸入組合繁多時驗證屬性，並行或多端狀態需要時考慮模型檢查，核心數學契約必要時才引入形式證明。
3. 執行相關檢查並保存可重跑證據。失敗時保留最短操作序列、反例或實際錯誤，建立可比較的前後結果。使用測試資料，依專案規則處理證據內的敏感資訊。若環境、工具或前置資料缺失，標明受影響的驗收條件。
4. 每項主張交付比對結果，包括版本、環境或夾具、命令或操作、預期與實際結果，以及測試報告、日誌、截圖、影片或模型輸出的位置。標明通過、失敗或未驗證。審查先查證據是否支持主張，再針對架構、資料變更或證據未覆蓋的高風險差異讀程式碼。審查中發現的同類問題，回饋成程式碼約束或新的驗證案例，讓下次不必再靠人工抓。

- UI、API 或 CLI 需要對齊功能詞彙、重跑流程、封裝操作或確認 Agent 理解意圖時，讀 [功能地圖與執行期證據](references/runtime-evidence.md)。
- 有大量輸入、並行狀態或數學契約時，讀 [屬性測試與形式驗證](references/invariants.md)。
